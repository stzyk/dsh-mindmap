### 几个实现细节

- **`MAX_DOCS` 用例没有跑 200 次原子写**：先用 `seed()` 一次性写入 200 份合法文档，再开 store 验证边界，全程约 5ms。
  另有一条 `MAX_DOCS + 7` 的**超量**用例，验证插件不会因历史数据超量而启动失败。
- **排序用例专门制造了「插入顺序 ≠ updatedAt 顺序」**：create A → create B 之后立刻断言
  `[B, A]`。如果实现退化成 Map 插入顺序，这条会立即失败（见变异测试 M3/M4）。
- **净化保障**：每个用例独立 `mkdtemp` + 设 `DSH_HOME`；`openAt()` 在每次 `openStore` 前
  先断言 `storageFile()` 落在临时目录内，因此**结构上不可能**污染真实 `~/.dsh`；
  文件末尾的 `after()` 再兜底比对真实存储文件的存在性是否与开跑时一致。
- **`~/.dsh` 那条只断言路径字符串**，全程不调用 `openStore`，并额外断言 `storageFile()`
  没有产生文件系统副作用。
- 用例串行执行（`DSH_HOME` 是进程级 env）；故意制造 `EACCES` 的用例会在清理阶段先恢复目录权限，
  避免留下删不掉的临时目录。

## 三、缺陷清单（**已全部修复**，保留记录供追溯）

### 缺陷 1 — 一次写盘失败会永久毒化写队列（严重）· 已修复

- **位置**：`src/store.ts:120`（`flush()` 里的 `writeChain = writeChain.then(...)`）
- **复现**：
  1. `openStore()` 后 `create()` 一份文档（成功）；
  2. `chmod(storages目录, 0o500)` 让写盘失败，`create()` 如预期 reject（EACCES）；
  3. `chmod(storages目录, 0o700)` 恢复可写，再次 `create()`。
- **期望**：第 3 步保存成功（一次失败的写只影响那一次调用）。
- **实际**：第 3 步仍然 reject EACCES，**该 store 实例之后的所有保存永久失败**。
- **原因**：`writeChain` 被赋成了已 rejected 的 promise，后续 `.then()` 全部连锁失败。
  需要在该链上挂 `.catch()` 做隔离（或每次 flush 用新的 Promise 兜底），保证失败不会传染到后续写入。
- **测试位**：`[已知缺陷] 磁盘写失败后写队列被永久毒化…`（todo）

### 缺陷 2 — 写盘失败后内存留下「幽灵文档」（中等）· 已修复

- **位置**：`src/store.ts:162-163`（`create`）、`182-183`（`save`）、`195-196`（`rename`）、`201-202`（`remove`）
- **复现**：同上（制造一次 EACCES 后让 `create()` reject），随后看 `store.list()`。
- **期望**：写失败的文档不留在内存里（内存与磁盘保持一致）。
- **实际**：`list()` 里多出一份从未落盘的文档；重新 `openStore` 后它凭空消失——
  调用方已经收到 reject，却无法知道内存里多了一份「假文档」。
- **原因**：先 `docs.set(...)` 再 `await flush()`，flush 抛错时内存已改、磁盘没改。
  建议写盘失败时回滚 Map，或把「内存已改但未落盘」显式标记为脏。
- **测试位**：`[已知缺陷] 写盘失败后 create 仍在内存留下幽灵文档…`（todo）

### 缺陷 3 — 超量加载后第一次写盘会静默删除磁盘上的文档（严重，数据丢失）· 已修复

- **位置**：`src/store.ts:95`（`if (docs.size >= MAX_DOCS) break;`）
- **复现**：
  1. 手工往存储文件写入 `MAX_DOCS + 7`（=207）份合法文档；
  2. `openStore()` —— 不抛错，`list()` 显示 200 份（这是任务书要求的「不能起不来」，OK）；
  3. 做一个与该数据无关的无害操作，例如 `rename("over-0", "改个名")`。
- **期望**：磁盘上的 207 份文档一份都不少（超量时应保留原文件 / 先备份 / 至少 warn 并拒绝覆盖写）。
- **实际**：`rename` 之后磁盘只剩 200 份，**超出的 7 份被永久删除**，整个过程没有任何 warn 日志。
- **原因**：加载期静默截断的 Map 在下一次 flush 时整体覆盖了原文件。
  插件在把用户数据载入内存时就丢了 7 份，之后任何一次保存都会把它写死。
- **测试位**：`[已知缺陷] 超量加载后第一次写盘会静默删除磁盘上超出的文档…`（todo）

### 附：非缺陷观察（供 Lead 参考）

- `openStore()` 会 `mkdir(storages)` —— 这是合理行为，但它意味着**只挂载插件就会在
  `~/.dsh/storages/` 下留下目录**。验收期间观察到真实环境里出现了一个
  `~/.dsh/storages/dsh-mindmap.json`（内容 `{"version":1,"docs":[]}`），
  已确认**不是本次测试写入**（跑测试前后该文件 mtime 未变），而是插件被装进真实 profile 后
  由 `src/index.ts:138` 的 `openStore()` 创建。
- `flush()` 里 `rename(temp, file)` 之后还跟了一次 `rm(temp, { force: true })`，属于冗余但无害的兜底。
